=== AC3 — per-order ETA computed from that order's own delivery-man coordinates, not a shared value ===
Live a11y dump (customer@nears.com, after admin-assigned delivery men + one order advanced to `handover`):
  Order #91131 (Nears Mart)   status=HANDOVER  DM=David Miller  "Arriving in 1 min"
  Order #91132 (The Grill House) status=HANDOVER (see note below) DM=D D  "Arriving in 999 min"
  Order #91145 (HealthCare Pharmacy) status=PENDING  no DM  "Waiting for a courier" (no ETA pill, correct per resolveEtaMinutes(hasDeliveryMan:false)=0)
Root cause of the differing ETAs (read from Admin/app/CentralLogics/Helpers.php deliverymen_data_formatting +
UserApp/lib/features/order/screens/order_tracking_hub_screen.dart _etaLabelFor / TrackDetailsViewWidget.resolveEtaMinutes):
  - David Miller (delivery_man_id=2) has ZERO rows in `delivery_histories` -> last_location is null -> lat/lng
    serialize as null -> distance defaults to 0 -> resolveEtaMinutes(distance:0, hasDeliveryMan:true) clamps to
    the floor, 1 min.
  - "D D" (delivery_man_id=4) has one `delivery_histories` row at Abu Dhabi coordinates (24.4538833, 54.3773433)
    while order #91132's delivery address is in the Dhaka (zone 1) seed data -> genuinely huge distance ->
    resolveEtaMinutes clamps to the ceiling, 999 min.
  This is a REAL per-order, per-delivery-man distance calculation (not a shared/first-order value) -- confirms AC3.

=== Environment instability (host-level, not NEARS-2670-specific) ===
- Booted a spare AVD (Pixel_10_Pro_3 -> emulator-5556) because both existing pool devices
  (emulator-5554, emulator-5558) were legitimately locked by other live QA sessions (NEARS-2423, NEARS-1695).
- Disk on emulator-5556 dropped from 1.27GB free at acquisition to ~660-680MB free (below the 800MB floor)
  over the course of the session; one `qa_disk_reclaim --clean` pass only recovered ~12MB.
- Repeated "app died, no saved state" / ActivityTaskManager force-removal entries in logcat, unrelated to any
  action I took at that exact moment; `lowmemorykiller` was actively killing unrelated system processes
  ("low watermark is breached").
- Both OTHER pool emulators (emulator-5554, emulator-5558) disconnected from adb entirely partway through this
  session (both vanished from `adb devices -l`) -- a host-wide resource-exhaustion event, not isolated to my
  own device or session.
- `uiautomator dump` itself was SIGKILL'd once (exit 137) under this pressure.
This degraded the back half of the session (AC5's full "hub already open" demonstration and AC7/RTL were not
reachable before I judged further live attempts unreliable) and is the proximate cause of the AC2 marker-color
inconclusiveness above. Recommend re-QA of AC2 (marker color), AC5 (full live demo) and AC7 (RTL) once host
capacity is available; this is an environment/capacity finding, not a code defect in NEARS-2670.
